# 软件需求规格说明书 (SRS)
## IinPublic – 基于位置的聊天机器人匹配与对话系统

---

## 1. 简介

### 1.1 目的
本软件需求规格说明书 (SRS) 描述了 **IinPublic** 应用程序的功能和非功能需求，这是一个去中心化、基于位置的聊天机器人通信和匹配系统。本文档主要供以下人员使用：
- 产品所有者和相关利益者（概念和范围）
- 架构师和开发人员（详细需求）
- 测试人员（推导测试计划和测试用例）
- UX 设计师（用户体验约束和期望）

### 1.2 范围
**IinPublic** 是一个优先采用 Web 端、后续推出移动端的去中心化应用，具备以下特点：
- 系统自动分配用户 ID 并根据位置将用户分配到基于位置的聊天室中。
- 用户可以创建和发送**对话 (talks)**（结构化的问答链）给附近的多名用户。
- 聊天机器人自动使用之前公开（自动）的回答来回复重复的问题。
- 用户可根据回答、位置、标签和声誉进行筛选、匹配，并建立一对一聊天。
- 系统支持：
  - 批量匹配（例如：寻找网球搭档、约会对象、买家/卖家、兴趣伙伴）。
  - 问卷调查（通过简单的对话收集汇总统计数据）。
  - 去中心化的声誉与防滥用机制（拉黑、反馈等）。

### 1.3 定义、首字母缩略词和缩写
- **对话 (Talk)**: 结构化的问答与预定义答案序列，可能包含分支（树状）。
- **自动回答 (Auto Answer)**: 用户标记为公开且聊天机器人可重复使用的回答。
- **手动回答 (Manual Answer)**: 私密且聊天机器人不会重复使用的回答。
- **聊天室 (Chatroom)**: 一个公开的、基于位置或自定义的“地点”，用户在此发现彼此；所有沟通仍保持一对一。
- **商业聊天室 (Business Chatroom)**: 绑定到特定品牌和地址（如某酒吧）的自定义聊天室。
- **旅行者 (Traveller)**: 身处模糊真实物理位置区域之外的聊天室中的用户。
- **标签 (Tag)**: 目录式标签（类似 Craigslist 分类），用于描述兴趣、物品或背景信息。
- **调查对话 (Survey Talk)**: 专门用于收集和汇总回答统计的对话。
- **声誉 (Reputation)**: 汇总的反馈指标（如：星级评分、拉黑次数、确认次数）。

本 SRS 其余部分安排如下：

## 2. 总体描述

### 2.1 产品视角
IinPublic 是一款：
- **去中心化**的、以 Gun.js 为后端的应用。
- Web 端优先（浏览器 + 内置 Node.js 实例），后续支持 Android 和 iOS。
- 使用层级式、基于位置的聊天室以管理规模的实时系统。

本产品不是传统的群聊：聊天室仅用于发现用户和路由分配；所有对话均保持一对一，并配有可选的聊天机器人参与。

### 2.2 产品功能（高层视角）
总体而言，系统提供以下功能：
- 自动分配用户身份并分配基于位置的聊天室。
- 层级式聊天室，容量超出时自动拆分。
- 以问答列表、化名 (StageName) 及声誉版块呈现的用户资料。
- 简单、预设的问答对话系统，不允许死循环，允许逻辑“或”(OR)。
- 向选定范围内的最多 N 名用户（如 1000 人）批量发送对话。
- 内置过滤器（语言、语法、脏话等）。
- 标签系统（类似 Craigslist），可快速按兴趣和物品过滤。
- 批量匹配逻辑，适用于约会、运动、买卖、找搭档等场景。
- 用于收集汇总统计数据的调查对话。
- 去中心化的管理与审核（拉黑、年龄限制、声誉屏蔽）。
- 带有聊天机器人覆盖图标的头像，用来区分机器人与真人回复。

### 2.3 用户分类与特征
- **普通用户**：寻找匹配对象（朋友、约会、搭档、买/卖家）。多非技术出身，需要简单的流程。
- **高阶用户 / 对话设计者**：设计复杂的对话和调查问卷。使用模板和标签进行精准投放。
- **企业主**：创建与物理位置绑定的商业聊天室。向客户发布调查问卷及目标对话。
- **未成年用户**：限制访问成人内容对话。
- **滥用 / 被拉黑用户**：受到声誉系统的严格限制，发送容量可能会被降低。

### 2.4 运行环境
- **Web**: 现代浏览器，JavaScript/TypeScript，浏览器内的 Node.js 实例。
- **Android**: 内嵌类似 Node 的运行环境并调用 GPS 的原生应用。
- **iOS**: 待定；类似功能可能需要采用其他实现方式。
- **后端/数据**: Gun.js 用于点对点的数据实时同步。

### 2.5 设计与实现的约束
- 去中心化架构，将中心化审核降到最低。
- Gun.js 相关约束（如最终一致性、对等连接限制、数据存储）。
- 移动端 GPS 获取“真实位置”，但对外操作时需进行位置模糊化以保护隐私。
- iOS 版内部运行 Node.js 存在不确定性。

### 2.6 假设与依赖
- 用户至少定期有网络连接；离线状态下的操作可延后同步。
- 移动端支持获取 GPS 或等同的位置数据。
- 品牌/Logo 及企业认证滥用争议将依赖相关法律规范；其余通过应用内声誉系统解决。
- 社区自发机制（如评价反馈、拉黑）对于滥用的缓解已足够有效。

## 3. 具体需求

### 3.1 功能需求

#### 3.1.1 用户管理与个性资料
- **FR‑UM‑1**: 系统 **必须** 在用户初次使用时分配唯一的 ID，无需强制传统登录。
- **FR‑UM‑2**: 系统 **必须** 要求每个用户输入必填项 **名号 (StageName)**。
- **FR‑UM‑3**: 用户资料 **必须** 用问答对列表形式呈现。
- **FR‑UM‑4**: 系统 **必须** 允许用户挑选一个 **头像图标** 作为个人形象。
- **FR‑UM‑5**: 若信息为机器人代答，对话界面的用户头像上 **必须** 叠加一个机器人标识小图标。
- **FR‑UM‑6**: 系统 **必须** 维护一个对该用户“只读”的 **声誉模块**，至少包含以下内容：
  - 问题回答总数
  - 对话发送总数
  - 成功匹配次数
  - 好友数及共同好友数
  - 星级评价
  - 年龄实名反馈 (真/假等票选统计)
  - 被别人拉黑的次数
- **FR‑UM‑7**: 用户 **可以** 对外隐藏全部或部分的声誉情况，但 **绝不能** 手工修改这些核心数据指标。
- **FR‑UM‑8**: 系统 **必须** 允许用户建立自己的有效名单（跨地区的联系人名录）保存记录。

#### 3.1.2 内置过滤模块
- **FR‑BF‑1**: 每段对话都 **必须** 标记清楚其所使用的主要语种。
- **FR‑BF‑2**: 系统 **必须** 记录好每个用户的能理解语种白名单。
- **FR‑BF‑3**: **语言过滤器** **必须** 自动屏蔽/忽略不在此前语言白名单内的话语（除非单独关闭此功能）。
- **FR‑BF‑4**: **语法过滤器** **必须** 会检视及可选舍弃包含大量错漏语法的劣质信息。
- **FR‑BF‑5**: **脏字过滤器** **必须** 能拦截含有明文违禁/不敬敏感词的文本。
- **FR‑BF‑6**: 用户端 **必须** 可以对这些设定分别启用/停用以及条件性调校灵敏度。

#### 3.1.3 频道（聊天室）控制 与 漫游/旅行 体系
- **FR‑CR‑1**: 整个应用框架基础下，**必须** 设有一个公开无差别的“全球频道”，所有端侧启用的初试用户都应能连接上。
- **FR‑CR‑2**: 新用户在没有别的行为前，**必须** 直接被派位到这个全球默认聊天室里。
- **FR‑CR‑3**: 当聊天室的人员数额溢出承载阈值 (比如 1000 人)，后台机制 **必须**:
  - 执行拆分。按地理层次关系分割：洲际 → 国家 → 省级/州级 → 城市级 → 等等不断细化。
  - 基于当前设备的 GPS 判断分派对应的新衍生频道中去执行。
- **FR‑CR‑4**: 由此系统自运行基于坐标创建出来的这类地方属性频道，普通用户 **绝对不可以** 操作删除。
- **FR‑CR‑5**: 但是用户 **必须** 能单独依据需创立起“用户定制化专属频道”（比如商业房间），也允许起名/修改及撤除。
- **FR‑CR‑6**: 创建出来的商业房间 **必须** 包含以下元素：品牌名、实体通信地址、持有者 ID 号，位置信息及详细背景陈述。
- **FR‑CR‑7**: 若是碰到了房满且依然有新人进来情况，系统 **必须**:
  - 计算分析出占坑停留最早就未活跃者；
  - 发布清退前通告；
  - 剔除该对象把坑腾出让出给新生力。
- **FR‑CR‑8**: 底层系统端会把准确的 GPS 信息做储存处理，但在前置的业务展现与互动端上应用 **必须** 以脱敏后的带边距的“模糊化定位范围”作掩饰处理来运行。
- **FR‑CR‑9**: 同一个自然用户，由于所带的物理经纬范围计算包含度问题，被允许同一时刻存在于若干符合当前“属地范围”属性限定的多间群组内里。
- **FR‑CR‑10**: 一个用户也 **可以** 对不是当前所处位置的非本地频道作有意识的“到访（旅游）”互动，但在同一特定时刻，目标外地频道只允许存在唯一一个，并且在此房里头必须悬挂带 **旅行访客(traveller)** 身份铭牌来与其他原居民做标识的特殊区分。

#### 3.1.4 提问与应答 架构模式
- **FR‑QA‑1**: 全部询问类型文本数据要求 **必须** 是简单文本字符串即可。以 '?' 结尾的即断定是被发出的一个“疑问”。
- **FR‑QA‑2**: 对于解答部分则 **必须** 限定必须是由既定范本供予下选。选项以不同形式体现（如：是否二选一、复选、距离范围条选择、亦或具体标签选择等）；应答选项应伴跟随在问题抛出之后且结束符号以 '.' 判断。
- **FR‑QA‑3**: 每一条被抛出的问题项下，**必须** 将“无视 (Ignore)”加入其中的候选反应中去。
- **FR‑QA‑4**: 系统架构里关于应答的数据属性支持形式 **必须** 含有两类:
  - **自动(Auto)**: 对全系统透明开放使用，并可直接授权让本方机器人代理在需要时对外代投送答案的种类。
  - **私密手动(Manual)**: 对系统隐蔽的选项形式。
- **FR‑QA‑5**: 当出现重样类相同发问并且用户的库中早已预存过了应对的 Auto 选项时候，用户代理(Chatbot) **必须** 执行自动弹发且明确被标志这就是机器人的动作代劳记录。
- **FR‑QA‑6**: 若属于那些曾经作了 Manual 动作隐私存设的数据：代理端 **可以** 做私下底内的消息提醒操作。然而 **不能** 在没人授意的情景之下自己抢出答话给外面的收信人看。

#### 3.1.5 关于分类标签的框架规划
- **FR‑TG‑1**: 对系统内标签的新建操作，全体被容许的用户 **必须** 皆享有随意新增的自由权力。
- **FR‑TG‑2**: 这套标签应该 **必须** 以类别作归集目录化摆列，就类似 Craigslist 在门户黄页上干的事 （例如有归纳成：卖货、房屋租赁、提供啥服务、某某社区群落、或者约会有缘人类）。
- **FR‑TG‑3**: 该框架支撑体系内这些标签项应允许附加并且挂载于下列业务实体之上使用：
  - 发起的连串“对话”(Talks) 主题上；
  - 单独某个特定的“提问”(Questions) 下；
  - 注册者用来刻画人设时用的“个人偏好标签（interests）”档位里。
- **FR‑TG‑4**: 平台统计端应支持按当前地理区块内的采用频率排布热词，把越热的发掘在创建新标签搜索中去供作下拉优选。
- **FR‑TG‑5**: 设置此内容的一大要求即作为发给接受者的事前筛选前提规则过滤判断使用。
- **FR‑TG‑6 (业务流硬性规定条文)**: 凡是由系统执行产生或人手自己设计的 Talk 流脚本，所有的一律第一步骤都是：“标签限定以及位置匹配设定”。且此先决匹配设定模块务必会 **置前** 嵌在那些真实的交流发问动作的前面展现且执行判定拦截。

#### 3.1.6 关于结构“剧情对话”(Talk) 的机制描述与触发流程
- **FR‑TK‑1**: “Talk” 本质作为数据定义，其流向导图必须明确限制成 **有向且不可回调循环成回路**(DAG形式)的面貌呈现出来。
- **FR‑TK‑2**: 编制后台或业务页面 **必须** 不可产生回路构建的机会给用户。
- **FR‑TK‑3**: 以主次骨干枝丫或者只靠单一前后串连来维系的流均被允可。
- **FR‑TK‑4**: “逻辑或者条件(OR)”是允许存在的：表现为在某些题目里的多式不一样的解答分支可以被设定指向下边同一个共同接着问出另外的一个题目上。
- **FR‑TK‑5**: “Talk” 之旅的尽头，关于那个“剧终问题”(Final question)必然也是 **只能** 留有下边两种结果支持操作：
  - "不再理睬他/她 (Ignore)" → 以切断此线路会话并将本端清静为结尾；
  - "有搞头，找这人实体真人详切接上线 (Let's talk in person)" → 即此路线达成了所谓配对确认(Match)。
- **FR‑TK‑6**: 对于 Talk 流的定义分类，应该允许加上个别带有 "**仅为了搜集调查意见 (Survey)**" 功能目的属性区别出来；它们带有被配置成用于最终去专门归置集中运算结果数据的专项提问内容节点。
- **FR‑TK‑7 (有关自动化把即兴聊天变为标准化Talk的获取功能机制要求)**: 若正处于两个人的一对一文本对话窗：假如用户 A 打出一条含有这种特殊识别编排语法的句子 `Question? Answer1; Answer2; ...; AnswerN.` 时：
  - 系统后台接收到之后，便要将 A 用户刚刚录入的用分号割开的一条条预设 AnswerX，渲染制作成可以供 B 端对象用触摸点选的 Chip 小控件呈现于界面下给对方选；
  - 如果对面选择点击了对应的，就把这作为有意义合乎情理的应对答复录进去并将剩余其余不再予采纳考量；随后业务往下正常推移让后边符合同样结构的话题相继承接；
  - 全过程一直推演到，一旦发现输入了一句话并非以疑问符号作为终点也没有备选项（通常意味着以“句号 '.'”打止陈述完结），就视作本轮即兴沟通动作到此了结：
  - 此时候系统需要默默将其这整个一环套一环从头直到尾所有的问及对端人做的所有决策，在库里自动收结固化下来并且归属于创建人(也就是A方本尊)。生成出一个 "**纯单向直线无树状分叉结构(Linear Talk) 的模板草图预案**"（带好前面的那个关于环境人群预界定的 Tag 等前提头文件了）并放入个人后台名下的预备方案存库内好待这哥日后直接找人广播利用起来用。
- **FR‑TK‑8 ((制图环境的局限说明)**: 如果说是复杂的那类带树叶经络网络或者特定被标识属于问卷类别（Survey) 的这类产品流结构方案——它们只能且仅仅可以，通过单独打开那个专辟的名为 `Talk Editor UI` 后台制作环境界面才能从零起步捏出；上面那条所介绍的一边单劈着线拉出的单股记录方案只能弄出线性流程。

#### 3.1.7 海量分发与匹对逻辑实现方案
- **FR‑BM‑1**: 用户 **必须** 可以对划定的圈子里边符合目标群众范围，在同个操作中向里头数量不唯一的受众群像下“群发(批量)”特定的某项方案对话动作体验去。
- **FR‑BM‑2**: 该数字最高限制标准 **必须** 置于上限参数中可被定义和管制着。初期为每一位系统户头设置的批量扩散基线封顶值为“单次顶天一千对象”，但也容许结合不同身份给到各人的弹性配给，可一直调配达至系统全局定死极值点上即止。
- **FR‑BM‑3**: 每个具体人的实际获得发讯承载实力指数额度需随自身个人信誉数据起落。若因经常由于表现遭受到了其它玩家集体操作“屏蔽拉黑”,便按阶梯罚退其最高容量极限能力去限制这户的动作发生力。
- **FR‑BM‑4**: 在系统实际接手这操作时，其对系统发出的那个带有 1000 转发名额总命令会变成 1000 套并不同享环境相互间隔状态独自前行的实例对话在推进。
- **FR‑BM‑5**: 可允许这指令落地的实施发出地的入口 **必须** 囊括包含：目前的系统智能切出的一般群、带店名的商铺群及某些自建社群、甚至是经过系统按照一定离我这儿的码距加上身上背挂有什么个签（Tags)后纯靠大网过滤罗列出来的指定目标合辑这四种操作环境对象上进行投射。
- 与前者相联动的补充限定要求：如果在前面的那个即时环境自动收取沉淀成了方案剧本的草案若也想参与这个向众海量人广播寻找缘分的过程，这剧本 **必须得必须** 在前面强制插入完标签筛选与关于限定地址的开头审核语句确认头后方能开跑发送动作。
