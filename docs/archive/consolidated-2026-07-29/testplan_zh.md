# IinPublic 测试计划
## 基于位置的聊天机器人匹配与对话系统

---

## 1. 简介

### 1.1 目的
本测试计划定义了测试策略、范围和方法，用于根据软件需求规格说明书 (SRS) 中规定的需求来验证 IinPublic 应用程序。它是以下人员的指南：
- 测试工程师和 QA 团队
- 执​​行单元和集成测试的开发人员
- 验证业务需求的产品负责人
- 评估系统就绪情况的利益相关者

### 1.2 范围
本测试计划涵盖：
- **功能测试**：SRS 中的所有功能需求 (FR-*)
- **非功能测试**：性能、安全性、可用性和可移植性需求
- **平台测试**：Web（浏览器 + 内嵌 Node.js）、Android 及未来的 iOS
- **集成测试**：Gun.js 集成、定位服务、实时通信
- **用户验收测试**：端到端用户场景和工作流

### 1.3 测试目标
- 验证所有功能需求是否均已正确实现
- 验证系统在负载下的性能（最多 1000 个并发会话）
- 确保满足安全和隐私要求
- 确认跨平台兼容性和一致性
- 测试离线/在线同步功能
- 验证去中心化架构的弹性

---

## 2. 测试策略

### 2.1 测试级别

#### 2.1.1 单元测试
- **范围**：各个函数、方法和组件
- **工具**：Jest、Mocha 或类似框架
- **覆盖率目标**：最低 80% 代码覆盖率
- **重点领域**：
  - 对话结构验证（DAG，无循环）
  - 过滤逻辑（语言、语法、脏话）
  - 自动回答与手动回答处理
  - 标签系统功能
  - 声誉计算

#### 2.1.2 集成测试
- **范围**：组件交互、Gun.js 集成、API 集成
- **重点领域**：
  - Gun.js 点对点通信
  - 定位服务集成
  - 聊天室管理
  - 对话执行引擎
  - 调查汇总系统

#### 2.1.3 系统测试
- **范围**：完整系统功能
- **环境**：镜像生产环境的暂存环境 (Staging environment)
- **重点领域**：
  - 端到端用户工作流
  - 负载下的性能
  - 安全和隐私
  - 跨平台一致性

#### 2.1.4 用户验收测试 (UAT)
- **范围**：业务场景和用户体验验证
- **参与者**：业务利益相关者、代表性用户
- **重点领域**：
  - 业务用例（约会、买卖、爱好匹配）
  - 用户界面可用性
  - 商业聊天室功能

### 2.2 测试类型

#### 2.2.1 功能测试
- 针对 SRS 需求的特性验证
- 边界条件测试
- 错误处理和验证
- 数据完整性验证

#### 2.2.2 性能测试
- **负载测试**：正常预期负载（每个聊天室最多 1000 名用户）
- **压力测试**：超出正常容量以发现崩溃点
- **数据量测试**：大量数据（对话、消息、用户配置资料）
- **可扩展性测试**：负载增加时的系统行为

#### 2.2.3 安全测试
- 位置隐私验证
- 用户数据保护
- 输入验证和清洗
- 身份验证和授权（适用时）

#### 2.2.4 兼容性测试
- **浏览器测试**：Chrome、Firefox、Safari、Edge
- **移动端测试**：各种 Android 设备和版本
- **网络测试**：不同的连接类型和速度

## 4. 详细测试用例

### 4.1 用户管理与配置资料测试

#### TC-UM-001：用户 ID 分配
- **目标**：验证首次使用时唯一用户 ID 的分配
- **前置条件**：干净的应用程序状态，无现有用户数据
- **步骤**：
  1. 首次启动应用程序
  2. 验证唯一 ID 是自动生成的
  3. 重新启动应用程序并验证保留了相同的 ID
- **预期结果**：分配了唯一 ID，跨会话处于持久状态

#### TC-UM-002：名号 (StageName) 管理
- **目标**：验证强制性 StageName 功能
- **步骤**：
  1. 新用户尝试在未设置 StageName 的情况下继续
  2. 设置有效的 StageName
  3. 尝试设置重复的 StageName（如果要求唯一性）
- **预期结果**：必须输入 StageName，验证逻辑正常工作

#### TC-UM-003：个人资料问答系统
- **目标**：验证作为问答列表的个人资料
- **步骤**：
  1. 回答各种问题以建立个人资料
  2. 修改现有答案
  3. 从另一个用户的角度查看个人资料
- **预期结果**：配置文件正确存储并显示问答对

#### TC-UM-004：声誉系统
- **目标**：验证声誉指标是只读且准确的
- **步骤**：
  1. 执行应影响声誉的操作
  2. 尝试直接修改声誉值
  3. 验证声誉计算是否正确
- **预期结果**：声誉自动更新，无法手动编辑

### 4.2 内置滤镜测试

#### TC-BF-001：语言过滤器
- **目标**：验证语言过滤功能是否正常工作
- **前置条件**：配置有特定语言偏好的用户
- **步骤**：
  1. 发送受支持语言的对话
  2. 发送不受支持语言的对话
  3. 切换语言过滤器的开/关
- **预期结果**：启用过滤器时，仅接收支持语言的对话

#### TC-BF-002：语法过滤器
- **目标**：验证语法错误检测和过滤
- **步骤**：
  1. 发送语法正确的对话
  2. 发送有重大语法错误的对话
  3. 测试各种灵敏度级别
- **预期结果**：语法过滤器可正确识别并过滤不良语法

#### TC-BF-003：脏话过滤器
- **目标**：验证对冒犯性内容的过滤
- **步骤**：
  1. 发送包含冒犯性术语的对话
  2. 发送包含处于边缘情况的内容的对话
  3. 测试过滤器的敏感度设置
- **预期结果**：对冒犯性内容进行适当过滤

### 4.3 聊天室管理测试

#### TC-CR-001：全局聊天室
- **目标**：验证全局聊天室功能
- **步骤**：
  1. 新用户加入应用程序
  2. 验证是在全局聊天室的位置
  3. 测试全局聊天室内的通信
- **预期结果**：所有新用户均在全局聊天室中启动

#### TC-CR-002：自动拆分房间
- **目标**：验证当超出容量时聊天室能够自动拆分
- **前置条件**：能够模拟 1000 名以上的用户
- **步骤**：
  1. 填满聊天室至容量阈值
  2. 添加其他用户
  3. 验证是否发生自动拆分
  4. 测试用户在适当子房间的位置
- **预期结果**：房间自动拆分，用户被移动到适当的位置

#### TC-CR-003：商业聊天室创建
- **目标**：验证商业聊天室功能
- **步骤**：
  1. 创建包含必填字段的商业聊天室
  2. 验证位置绑定
  3. 测试商业特定功能
- **预期结果**：使用所有必需属性创建的商业聊天室

#### TC-CR-004：旅行者功能
- **目标**：测试远程聊天室访问
- **步骤**：
  1. 用户出差至远程聊天室
  2. 验证标记了旅行者状态
  3. 测试作为旅行者的限制和功能
- **预期结果**：正确应用和执行旅行者状态

### 4.4 问答系统测试

#### TC-QA-001：问题格式验证
- **目标**：验证问题格式要求
- **步骤**：
  1. 创建以“？”结尾的问题
  2. 尝试无效的问题格式
  3. 验证出现的验证消息
- **预期结果**：仅接受有效的问题格式

#### TC-QA-002：选项配置
- **目标**：测试预定义的答案功能
- **步骤**：
  1. 创建具有各种回答类型（二元选项、多项选择、范围值）的问题
  2. 测试“忽略”选项的可用性
  3. 验证选项选择工作是否正常
- **预期结果**：所有答复类型均正常，并且“忽略”项始终可用

#### TC-QA-003：自动与手动回答
- **目标**：验证自动/手动回答功能
- **步骤**：
  1. 将答案设置为“自动”，并测试机器人的重复利用
  2. 将答案设置为“手动”，并验证没有自动重复利用
  3. 为自动回复的机器人图标遮罩层进行测试
- **预期结果**：机器人会重复使用“自动回答”，而不会使用“手动回答”

### 4.5 会话结构和执行测试

#### TC-TK-001：Talk 的结构验证
- **目标**：验证 DAG 结构实施（无循环）
- **步骤**：
  1. 创建有效的树状结构对话
  2. 尝试使用循环创建对话
  3. 测试逻辑 OR 函数
- **预期结果**：接受有效的结构，防止循环发生

#### TC-TK-002：自动线性捕获
- **目标**：测试从聊天中自动捕捉 Talk
- **前置条件**：以一对一聊天形式出现的两位用户
- **步骤**：
  1. 用户 A 传送：“你喜欢喝咖啡吗？是的; 不是。”
  2. 用户 B 选取“是的”
  3. 用户 A 传送：“热的还是加冰的？ 热的; 加冰的。”
  4. 用户 B 选取“加冰的”
  5. 用户 A 发送：“太棒了，我们明天见。” （无答案选项）
- **预期结果**：
  - 预定义的选项显示为可操作的卡片 (chips)
  - 自动建立线性 Talk，并且存储为草稿
  - 自动引入标签/位置前置内容

#### TC-TK-003：对话编辑器功能
- **目标**：验证 Talk Editor 的能力
- **步骤**：
  1. 在编辑器中建立树形结构对话
  2. 在编辑器中创建问卷调查 (Survey Talk)
  3. 对分支和 OR 连接进行功能测试
  4. 验证循环预防情况
- **预期结果**：编辑器可以支持所有须有的会话类型和结构

### 4.6 批次匹配并进行传送操作检验

#### TC-BM-001：批量发送功能
- **目标**：针对海量收件人传送进行检测
- **前置条件**：该聊天室内有存在的目标对象群体
- **步骤**：
  1. 根据应属的过滤标签建立对谈
  2. 对最多支持数量的接收人发送（即预设为 1000 名）
  3. 对能否正常分别产出个别且独立的话语进行检验
  4. 随进反馈回复比与触达情况
- **预期结果**：符合资质的受众正常可收此询访，并且创建隔离各自独立的沟通

#### TC-BM-002：寻找网球伙伴（依样于 SRS 中的例子）
- **目标**：综合性寻找网球伙伴验证工作
- **前置条件**：处于相同市级范围而具备相同爱好的户主库人群
- **步骤**：
  1. 附带有层级区分度网球同行的配对
  2. 根据带有运动、网球标签实施大量的转发扩散工作
  3. 回溯在所有对发中产生的提问情况
  4. 验证对于选择了“当下面聊聊吧”所能生建之联结确认情况
- **预期结果**：仅仅剩下那些相切合者至底部的结案环节，适当连结配对

#### TC-BM-003：声望数值限定群散限制量
- **目标**：测试是否因声望程度而在发送限额上有差幅
- **步骤**：
  1. 操作名声正向积分拥有者进行推传
  2. 使用多次在过去被列向他人黑名薄对象的应用作发推
  3. 做双向比差其两端的允许最高群量规模
- **预期结果**：信誉不堪的人发送极限量被压低处理

### 4.7 针对特定采意调查方案操作检验要求条目

#### TC-SV-001：意向采整对话(Survey) 的架构设与放行执行
- **目标**：证实此类的运作正常行不通行
- **前置条件**：属于那商业型带有群众多之空间场景大堂一所在
- **步骤**：
  1. 设置含具有数据积数统量设及的题目项目
  2. 撒网置往所处的该企业大院成员面前内中去
  3. 将众多客户收集其回复结果信息
  4. 去印证统记数值与分类合数的结果实数计算结果
- **预期结果**：采集表收集反馈数精确并合并生成数图的正确计算

#### TC-SV-002：消费者评分调研 (沿用 SRS 场景参考样）
- **目标**：完整的用户评核打粉之验证应用案例
- **步骤**：
  1. 商户起草一套用于回馈消费体验度的核定问卷
  2. 推给大堂内里全部在此停留消费的人员受访
  3. 各号对象响应各层阶的星等打点
  4. 核查这盘数是否合计出不出半星出入
  5. 检测一下选择要求追踪访客对其实连信开启的效果
- **预期结果**：数值精确体现不失，选择跟商家接洽者亦获提供交流连线口

### 4.8 控制发散防御及把关制度验证工作条例指示
#### TC-SP-001：限制连收发的定频限幅验证
- **目标**：针对发送接纳限频作校验
- **步骤**：
  1. 设计超越单日单回传的强撞动作尝试破限数量度
  2. 去落实查验对接收和传是否做有一视等量定频(不偏颇同量限制)之把门规则要求
  3. 检测是否定期自动放额清卡复原
- **预期结果**：成功制掣超出者限封行为

#### TC-SP-002：黑牌与阻止权限测试
- **目标**：对拉黑用户的执行系统检验
- **步骤**：
  1. 对象户A 向 B户进行投禁锁之动作
  2. 要验证到 B绝对没办法去用该应用把字送到这一端上面去的防禁功效
  3. 同时也不能再去A那档前观看相关门面板子资料
  4. 关于对自我名下的名单做修治的操作确认顺当畅
- **预期结果**：锁定及防越权干预全封功效有效达成

#### TC-SP-003：对限满及成人类内容信息隔截要求之规验
- **目标**：限缩部分有色或者是十八限制类东西的安全管制效用检测的落地核准
- **步骤**：
  1. 造出挂置这种不适合小鬼看见标识标签前提问题的话术方案
  2. 指定开没成满的用户角来对其对位推看看
  3. 回同选让成人级试行能否照过
  4. 同时校验年龄审核对个各评价度(人品数值等参数收集那部段中)里的声值数给没加进
- **预期结果**：禁类者决入全遮挡功能生效且那参数也有跟入进去记号了的

### 4.9 分捡项签标验证

#### TC-TG-001：自建标签及能列位建库检验
- **目标**：针其体系架构做测试验证有效果不没
- **步骤**：
  1. 建带像类似那拉皮黄页式的大集下设建一些特签的名号
  2. 给个个的对号座把提话甚至人面里打那记号归起边在上面的各部件模块下应用
  3. 将区域间这热门打标频率追进排行做个演试和排序机制检测看有没出没
  4. 对着去给个带拉配找找这个匹配建议系统看看有效没有推给来建用着看其灵活性程度。
- **预期结果**：设标成出且带进统类里而且推用建用着灵捷热度排位正准

#### TC-TG-002：带着标记强制入列发门前审核防呆预验证的设置
- **目标**：看看在进首发程序时这必须走强制位定标签步骤有没有卡得主卡得对门路
- **步骤**：
  1. 故意去避开去省掉那定位置弄好前提便硬想制开对话发的话的流程试一回其错处去给能成功否动作。
  2. 让机上报验证出错并挡截系统防不有给阻强其制通过执行。
  3. 后去带着正规的批上那些签发的步骤去重干一遍检测它通不通行不行的。
- **预期结果**：必然是要带上前门签配那类定位才能打得出去了是这规没。

### 4.10 分端口在平稳相跨相一致上的考验要求规范
#### TC-PS-001：桌面互联网等主端口上作平检测
- **目标**：对基于纯这那 Web平展面中运行有效程度进行的验收
- **测距方组**:
  - 用谷歌 Chrome（其前最新老代更选对配各套用着来看表现跑)
  - 对这火狐和那 Safari 以此推各一套验过测
  - 对了不忘了微软自这Edge也上一遍这些主流跑遍套组。
- **步骤**: 各带浏览器跑上面核心业务一的流程大过不不。
- **预期结果**：一样齐不乱，步步相一和协功能平一稳顺通等结果达成!

#### TC-PS-002：向安置机器人移动智能这系统这Android端口阵测验
- **目标**: 将其之同能有于机中作的功效查定
