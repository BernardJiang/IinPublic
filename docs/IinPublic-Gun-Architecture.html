IinPublic — Gun.js Database Architecture

A public self-definition platform, NOT a chat app. Identity = Q&A list + 4 talk types + SEA-encrypted interactions.

The Three Pillars

Pillar 1 — Profile Q&A

Each user builds a QuestionAnswer[]. Auto-generated or manual. Visibility: public | contacts_only | private.

Pillar 2 — Talks (4 Types)

Structured interaction templates broadcast via Gun mesh:

  • tag — single keyword toggle
  • flow — linear Q/A chain (path graph)
  • survey — independent polls (star graph)
  • route — branching DAG w/ FNV-1a hash

Pillar 3 — Interactions

Conversations triggered by talk matches. Two-writer message DAG with SEA+ECDH encryption. Every interaction cryptographically signed in append-only ledger.

Gun Graph Structure

All data lives in Gun.js graph paths. Two users (A and B) share a mesh; their personal data flows through the same topology.

Two-Person Interaction Flow

How Two people share their interactions from start to finish:

Step 1 — A creates + broadcasts a talk
A defines a Talk (type: tag|flow|survey|route) stored at talks/<id>. Ledger event TALK_CREATED signed via SEA. Broadcast to chatrooms + mesh delivers copies + peer discovery via tags.
Step 2 — B receives talk delivery
Gun mesh pushes to receiver's node. Cluster merged into ownerIncomingTalkIndex/B/<identityKey>. Ledger event TALK_RECEIVED recorded. Incoming talk filter (distance, language, blockByWords...) applied per user-talk-filters/B. Content-hash-based identityKey ensures one topic per person — NOT 47 duplicates.
Step 3 — B answers
B submits answers stored at conversations/<convId>/answers<qId>. Ledger event TALK_ANSWERED with outcome (match|mismatch|ignore).
Step 4 — Match occurs
When answers trigger match: conversation created at conversations/<convId>. Both participants indexed under users/A/conversations/..} and users/B/conversations/.... Ledger event MATCH_CREATED.
Step 5 — Messages exchanged
Each message persisted to Gun with idempotent writes. Stored in BOTH mesh path AND pair-private path. For non-public channels, text encrypted via SEA-ECDH: SEA.encrypt(text, SEA.secret(peerEpub, myPair)). prevSeenDAG link forms two-writer DAG for deterministic offline merge.
Step 6 — Delta-sync converges
Both peers publish ledger/{id}/state containing highest seq per user feed. Read peer's state → compute missing events pushed to ledger/peerId/inbox/<eventId>. Inbox subscription ingests remote events with SEA sig verification.

Encryption Model

SEA Signing Keys (pub/priv)

Used for: signing ledger events, talk authorship proof. Published to mesh at users/id/pub. Every event carry SEA signature verified by any reader.

SEA Ephemeral Keys (epub/epriv)

Used for: ECDH shared-secret derivation between peers. Each pair shares secret via SEA.secret(epub_A, pair_B) or vice versa.

Message Encryption

When channel is not public, text encrypted with shared secret:
SEA.encrypt(plainText, sharedSecret)
Decrypted on read with owner's epriv key. Two-writer DAG ensures deterministic offline merge without central sequencer.

Key Custody

Full keypair stored in localStorage as AES-GCM ciphertext wrapped by PBKDF2-SHA256 (150k iterations). Supports export/recovery via signed recovery package.

Data Ownership & Retention Policy

Gun.js replicates all subscribed graph nodes locally — no built-in scope boundary. This tiered policy defines what the local node should keep and for how long. See Gun-Database-Architecture.md §8 for full rationale.

Chain integrity constraint: Ledger prev pointers form a hash-linked chain. Deleting events in the middle severs verifiability. A pruning operation MUST write a signed merkle checkpoint for the range before deleting any events. The checkpoint is the only evidence those events existed — and it is sufficient for O(log N) proof verification.

Blockchain-Style Integrity During Trim

The ledger and message history use the same pattern as Bitcoin SPV: prune old entries but keep a signed merkle root that commits to all of them. See Gun-Database-Architecture.md §9 for the full verification protocol.

Merkle Checkpoint (Ledger)

Every N=100 events: compute SHA-256 of sorted CIDv1 array → sign with SEA key → write as CHECKPOINT_CREATED event at ledger/<userId>/checkpoints/seq_N. Keep last M=500 events in full detail; prune older ranges.

Storage: 256 bytes/checkpoint vs 35 KB/100 events → 99.3% reduction

Merkle Checkpoint (Messages)

Every K=50 messages: compute SHA-256 of sorted [msgId + SHA-256(ciphertext)] pairs → sign → write at pairConversations/…/checkpoints/<seq>. Keep last 200 messages/conversation in full detail.

Storage: 512 bytes/checkpoint vs 40 KB/50 messages → 98.8% reduction

Verification Protocol

To prove event E existed after pruning: (1) locate checkpoint for E's range; (2) return checkpoint (merkle root + SEA sig) + 7-hash merkle proof path for E's CID; (3) verifier checks SEA sig + merkle path. Cost: O(log N) ≈ 7 hash comparisons for N=100.

Net Storage Impact

Power user (50 convs × 2,000 msgs): without pruning ~97 MB; with pruning (keep 200 msgs + 500 ledger events in full) → ~10 MB (90% reduction). Pruned content is proven-committed but not reconstructible — which is the correct privacy posture for old messages.
