# 2026-10-04

- Product decision: chatrooms are hard P2P traffic partitions, not merely UI groups. Each device has exactly one active exchange room; inactive memberships create no discovery, radio presence, gossip, or automatic peer links. Users manually switch rooms to reach more people over time.
- Scaling uses two independent limits: global room capacity `C = 498` bounds each client's candidate/active set and sparse neighbor limit `K` bounds live automatic links per device (target 8–16). One million users therefore occupy at least 2,009 room overlays rather than a global graph with about 500 billion possible pairs.

## Chatrooms have no privileged creator

- Product decision: creating a local, business, or custom chatroom only makes the creator its first ordinary participant. There are no room owners, moderators, privileged roles, or reserved creator seats; the creator can be FIFO-evicted when full.
- Any user may publish a room. The P2P protocol does not enforce trademarks or reserve display names; cryptographic room IDs distinguish duplicates.
- Capacity remains one global protocol value. For a `498 → 1000` upgrade, the same room keeps its ID and active users, 502 positions open, and evicted users are not auto-restored.
- Future-proof release decision: each release embeds the next release's public verification key and a generic protocol-manifest engine. The next release carries an offline-signed, hash-chained manifest containing the global capacity/epoch and the following public key. Any peer can relay it; compatible old clients verify and apply it before exchanging room traffic, without reinstalling.
- Release private keys never ship in the app. Persist monotonic manifest checkpoints, reject rollback/same-sequence forks, enforce compiled parameter safety bounds, and pin separate threshold recovery keys for loss/compromise of the ordinary one-time next key.
- A manifest authenticates authorized protocol parameters, not the binary running on a peer. Honest clients still validate all messages; exact remote-binary proof would require platform attestation and an online trust service.
- A newer release carries the signed public manifest history required by the oldest supported trust checkpoint, not historical private keys. Release 1 can verify release 3 by validating M2 with pinned K2.public, learning K3.public, then validating M3. Applications may be skipped; manifest links may not.
- Release 1 must define the future-compatibility state machine before production: dynamic safe parameters, optional capability intersection, mandatory-capability/protocol failure, critical unknown fields, and authenticated retirement into local-only/update-required mode without locking user data.
- An isolated old client cannot know a later release exists. Product must choose before release 1 between perpetual legacy availability (recommended) and an expiring P2P-renewable protocol lease that sacrifices indefinite offline operation.
- Coordinator-free P2P cannot guarantee an instantaneous globally exact FIFO roster under network partition. `C` and `K` are hard local traffic bounds; room membership converges from signed expiring presence.
